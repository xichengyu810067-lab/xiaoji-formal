# Optional extension contract

The public core may load one local CommonJS extension only when `XIAOJI_PRIVATE_EXTENSION_PATH` is set to an absolute file or directory path. Absence of this variable is a supported public-core mode.

An extension exports `apiVersion: 1`, a stable `id`, optional command directories, deployment targets, interaction guards, and hooks. The host currently supports:

- `guards.interaction`
- `hooks.interactionCreate` and `hooks.messageCreate` (reserved for board and other isolated routers)
- `hooks.guildMemberAdd`, `hooks.ready`, and `hooks.shutdown`
- `hooks.channelDelete` and `hooks.voiceStateUpdate`
- `hooks.publicCommandCompleted`
- `hooks.workRole.syncJobRoleForMember`
- `hooks.workRole.removeJobRoleForMember`
- `hooks.workRole.removeJobRolesForMember` (the core does not call this hook at present: resigning is not offered, so `/work cancel` removes no job roles; the hook itself is unchanged)
- `hooks.workRole.syncAllJobRoles`
- `hooks.workRole.syncPrimaryJobRoleForMember`
- `hooks.workRole.clearPrimaryJobRoleForMember`

The last two belong to a member's single global primary job. The core runs a hook only for an extension that exports it, and reads the first answer that is not `undefined`:

- `hooks.workRole.syncPrimaryJobRoleForMember({ member, jobName, options })` runs for `/work role-sync` with a user, once, when that user's primary job is active and was started in the guild where the command runs. `member` is the guild member, `jobName` the name of the primary job, `options.cycleId` the id of its active cycle and `options.sourceGuildId` the guild it was started in. Only the `warnings` of the answer (a list of text lines) are used: the core adds them to its reply. With no answer, or a falsy one, the answer is `{ ok: true, skipped: true, role: null, warnings: [] }`.
- `hooks.workRole.clearPrimaryJobRoleForMember({ client, cycleId, userId, sourceGuildId })` runs once for each primary-job cycle, right after the scheduled payroll has settled it and committed the settlement, and never when that run has no Discord client. `cycleId` is the settled cycle, `userId` the worker and `sourceGuildId` the guild the job was started in. An answer with `ok: false`, or a hook that throws, is logged as a warning and counted as a failed cleanup (`roleCleanupFailed`) in the result of the run; the settlement is never undone. With no answer, or a falsy one, the answer is `{ skipped: true }`.
- `hooks.workRole.syncAllJobRoles({ guild })` runs for `/work role-sync` without a user. The core reads `total`, `synced`, `cleaned` (optional) and `warnings` of the answer and shows them. An answer that stopped before every role was synced (a role change deferred for its budget, or a role queue that could not take it) sets `rateLimited: true`, and `queueFull: true` as well for a full queue; then the core titles its reply as paused instead of complete and shows the first warnings, so the reason for the stop should be the first warning. With no answer, or a falsy one, the answer is `{ total: 0, synced: 0, warnings: [], skipped: true }`.

Each private command-directory descriptor may declare its own `guildIds`. Descriptors without `guildIds` retain the extension-level deployment scope for compatibility. Commands from multiple groups are unioned only within guilds shared by those groups. Cleanup may target only guilds no longer owned by any command group and must read back this application's existing guild commands before clearing them.

Private commands must be registered only to their declared guilds. Runtime guards and each background or role side effect must independently enforce the same scope. Owner identity never bypasses the extension scope. Public commands remain global and keep their own existing permission checks. The public core ships no owner-only command: an owner-only command is a command of an extension, in a command group whose `guildIds` hold the owner guild (`XIAOJI_OWNER_GUILD_ID`, one Discord ID, or an empty list when it is not set), and it checks that guild again in its own `execute`. The deployment code can still place a whole command that the public catalog marks owner-only in the owner guild alone; when it does, and a command group also targets the owner guild, both go out in the same request and a name collision refuses the deployment.

## Discord request boundary

Calls made while a verified extension command, guard, hook or preflight runs carry an extension context. The public core opens that context only after assembly-manifest verification. For a command (its execute or autocomplete handler) the context also records, from the interaction the host runs it for, the user who ran it and that interaction: its id and a SHA-256 digest of its token, never the token itself. Hooks, guards and preflights record neither, even when their payload holds an interaction. Only the host opens the context. An extension must not open or rewrite a context itself, for example by calling `client.extensionHost.runCommand` or `runWithHostOperationContext`; this is a duty of the extension under this contract, not something the host can enforce, as the threat model below explains. Nor must an extension try to create its own REST client or replace `client.rest.request`. Nor may it use `queueRequest`, `setAgent` or `client.rest.options` to get around that wrapper: `queueRequest` accepts only the requests `client.rest.request` is sending, and the REST agent, API base and API version stay as they were at startup.

The request boundary allows a non-public Discord write only when that context is present and the destination guild is listed in `XIAOJI_PROTECTED_GUILD_IDS`. The bot never sends bulk bans, member pruning or guild deletion requests, and it never leaves a guild in that list. A private command may request a leave only for a guild outside the list, only while it runs for an interaction in a guild of that list, and only when both the user its context records as having run it and the host-operation actor are the configured owner; hooks, guards and preflights cannot leave a guild. A command's autocomplete handler runs as that command, so the same rule applies to it. Such leaves share one bot-wide cap: at most 3 leaves an hour and 10 in 24 hours, counted in process. The bot itself reviews no guild and leaves none on its own, so the extension command is the only way the bot leaves a guild. Requests made in the extension context cannot upload files, with one exception: a command running for an interaction in a guild of that list may answer that same interaction (its initial response, a follow-up message, or an edit of one of its messages) with one file. That file must be UTF-8 text of at most 1 MiB, as given and as sent; its name may hold only ASCII letters, digits, `_`, `-` and single dots, must start with a letter or digit, must end in `.json`, `.txt` or `.csv` (lower case) and may be at most 128 characters long. Its links are rewritten like any other outgoing text, it is sent with the content type of its kind, and the body may rename it only to a name that follows the same rule. Any other request of the extension context that carries a file is refused, and so is every protected delivery that carries one.

All outgoing text is checked for links. Unapproved URLs are replaced, and URL-only fields such as embed images or link buttons are removed. An address with `https://` followed by a character that is not ASCII (an emoji, a symbol or a look-alike letter, as in `https://🎁.ws/x`) is replaced whole when the URL parser a browser opens it with reads the run up to the next space as a host: an IPv4 or IPv6 address in any spelling (`https://０x7f000001`, `https://９３。１８４。２１６。３４`), or a name of two labels or more whose last label is an ending (letters, digits and hyphens of ASCII, the name of a top-level domain written in other letters such as `台灣` or `рф`, or a label written as `xn--`), with look-alike letters, digits, the ideographic full stop and invisible characters mapped as the parser maps them (`https://ⓔⓥⓘⓛ。ⓒⓞⓜ`, `https://「a@evil.com`). When the parser refuses a run for an invisible character (a zero width joiner, a tag character, a mark of direction), the run without them is read too, as older clients read it. A run the parser refuses or reads as one label (`網址要以https://開頭`), a run that ends at a mark of Chinese punctuation (`https://開頭，版本v1.1.2以後都支援`), and a last label that is a sentence, a word of a language that no top-level domain is, or a mix of ASCII and other letters (`https://開頭。這樣比較安全`, `https://開頭.不要用http`) are text. A last label that is an ASCII word or the name of a top-level domain (`https://開頭。OK`) cannot be told from a host, and is removed whole. An approved link wrapped in Markdown emphasis (`**https://discord.gg/…**`) is kept, with the markers outside it. A name written without a scheme that Discord may show as a link (for example `example.com/page`, `bit.ly/abc` or `discord.gg/…`) is replaced like a URL, with its port, path, query and fragment, unless it is an approved page. Version numbers and e-mail addresses are not links, and neither is a file name whose ending is not on the list of link endings (`README.md`, `main.py`, `data.json`); a file name that ends like a link ending (`requirements.in`, `model.pt`, `book.mobi`, `logo.ai`) is replaced. A name whose label in front of the ending is made of Chinese, Japanese or Korean letters alone is a link only with a port, path, query or fragment. The identifier of a component (`custom_id`) and the `value` of a select option or an autocomplete choice are never read for such names, and neither is the content of an uploaded text file; links with a scheme and invites are removed from all of them. A forwarded message (`message_reference` of type 1) is refused with `EGRESS_FORWARD_BLOCKED`, because the content it carries is added by Discord after the check. A protected delivery that would need a replacement is refused like one with a URL, so text from outside must be cleaned before it is sent. In a protected guild, explicit `@everyone` and role mentions from a verified extension are retained; elsewhere they are removed. Extensions should treat a refused request as a normal operational failure and must not retry it through a different network API.

The request boundary and the REST entry lock are defense in depth within one process: they stop an extension that is buggy but honest from sending a request the rules forbid by accident. They do not contain a hostile extension, which shares the process with the host and could still read the bot token, replace the global dispatcher, or patch prototype methods. The real boundary is therefore the assembly-manifest verification, code review and this contract, not these locks.

## Output budgets

The host applies output budgets after route validation. They are counted in process, shared with the public core and cannot be raised by an extension: message creates and edits allow 20 per channel per 10 seconds, reactions 10 per channel per 10 seconds, and DM-channel creation allows 30 per hour globally and 3 per recipient per hour. Outside the protected-guild budgets below, member mutations (including kicks, bans, timeouts and role changes) share a 5-per-guild-per-hour budget, and any other private write also shares a conservative 5-per-guild-per-hour budget, so a newly introduced Discord management route is never an unlimited bypass.

Outside the protected-guild budgets, bulk deletion and the deletion of single messages share at most 3 operations per channel per 10 minutes, and channel deletion allows at most 2 per guild per day. Each bulk deletion request must contain 2 to 100 message IDs, in a protected guild too. The host always blocks bulk bans, member pruning and guild deletion. A budget refusal is a deferral, not evidence that Discord received the request; extensions must return control to the host and wait for a later, independently authorized invocation.

The management requests a verified extension sends, in its context, to a guild listed in `XIAOJI_PROTECTED_GUILD_IDS` use wider budgets instead, so that ordinary moderation and upkeep of those guilds fit. They are the named constants `PROTECTED_GUILD_LIMITS` of the egress limiter:

| Requests in a protected guild | Budget |
| --- | --- |
| Member sanctions: bans, unbans, kicks, timeouts and any other change of a member itself | 30 per guild per hour |
| Adding or removing a role of a member, role syncs included | 300 per guild per hour, and at most 30 per guild per minute |
| Deleting single messages | 200 per guild per hour |
| Bulk deletions | 10 per channel per 10 minutes |
| Deleting channels | 20 per guild per day |
| Creating channels | 20 per guild per day |
| Any other private write | 60 per guild per hour |

Within a protected guild every sanction of the extension draws on the same budget, whether an automatic filter or the owner's own command asked for it: the owner cannot bypass it. The same holds for the other budgets in the table. The per-minute role window keeps a long role sync to a steady pace: a sync that goes faster is deferred, not queued, and the rest of it has to run again later. Requests made outside the extension context, and requests to any other guild, keep the budgets above.
